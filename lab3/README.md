# Лабораторная работа 3 — вариант 4: многопоточная TimSort

## Сборка и запуск

```
make
./timsort -t 4 -n 1000000 -c     # 4 потока, 1 000 000 элементов, проверка через std::sort
./timsort -t 3 -n 20 -p          # маленький массив с выводом до и после сортировки
```

Ключи:

| ключ | смысл |
|---|---|
| `-t N` | максимальное число потоков, работающих одновременно (обязательный) |
| `-n N` | размер массива (по умолчанию 1 000 000) |
| `-s N` | seed генератора случайных чисел |
| `-p` | вывести массив до и после сортировки |
| `-c` | сравнить результат с `std::sort` |

## Алгоритм

Используется упрощённая TimSort:

1. Вычисляется `minrun` (32..64) так же, как в настоящей TimSort.
2. Массив делится на куски длины `minrun`, и каждый кусок сортируется вставками.
3. Отсортированные куски попарно сливаются: сначала куски длины `minrun`,
   потом `2*minrun`, `4*minrun` и так далее, пока не останется один кусок.

Распараллеливание: куски на шаге 2 не зависят друг от друга, и все слияния одного
уровня на шаге 3 тоже. Поэтому задачи каждого этапа делятся поровну между
`min(N, число задач)` потоками (`pthread_create`). Главный поток ждёт их через `pthread_join`
и только после этого переходит к следующему уровню. Так одновременно работает не больше `N` потоков.

## Как посмотреть число потоков средствами ОС

```
./show_threads.sh 4             # запускает сортировку большого массива и опрашивает ps
```

Внутри используется `ps -M -p <pid>` на macOS и `ps -T -p <pid>` на Linux.
Ещё можно смотреть в `top`/`htop` (на Linux `htop` с потоками или `cat /proc/<pid>/status | grep Threads`).
PID программа печатает при запуске.

Пример вывода для `-t 8`: число потоков процесса меняется так

```
1   - главный поток генерирует массив
9   - главный + 8 рабочих (сортировка кусков и нижние уровни слияния)
5   - на уровне, где осталось 4 слияния
3   - 2 слияния
2   - последнее слияние (1 рабочий поток)
```

Больше `1 + N` потоков не бывает никогда.

## Выводы

1. **Маленькие массивы (10⁴–10⁵)**: ускорение маленькое или его нет вообще (при 16–32 потоках
   программа даже медленнее). Сама сортировка занимает меньше миллисекунды, а потоки
   создаются заново на каждом этапе. Этапов примерно `log2(n / minrun)`, то есть 10–15,
   и создание с ожиданием потока стоит десятки микросекунд. Накладные расходы
   оказываются больше полезной работы.

2. **Большие массивы (10⁶ и больше)**: на 2 и 4 потоках ускорение почти линейное
   (эффективность 0.85–0.95). Работы много, и накладные расходы на потоки малы по сравнению с ней.

3. **После 4 потоков рост замедляется.** У M4 только 4 быстрых ядра, остальные 6 медленнее.
   Потоки на них делают ту же работу дольше, а этап заканчивается только тогда,
   когда закончил самый медленный поток. Кроме того, слияние в основном копирует память,
   и при многих потоках упирается в пропускную способность памяти.

4. **Верхние уровни слияния почти последовательные (закон Амдала).** На последнем
   уровне всего одно слияние длины `n`, и его делает один поток. На предпоследнем
   два слияния, то есть работают только 2 потока, и так далее. Значит, сколько бы
   потоков ни было, последние уровни выполняются почти последовательно. Это ограничивает
   максимальное ускорение примерно 5 разами, что и видно в таблице.

5. **16–32 потока немного лучше, чем 8–10**, хотя ядер всего 10. Когда задач больше,
   чем ядер, ОС может перекидывать потоки: быстрые ядра, закончив свою часть,
   берут следующий поток. Медленные ядра перестают тормозить весь этап.
   Но эффективность при этом падает (0.16 при 32 потоках), то есть ресурсы тратятся впустую.

6. Оптимальное число потоков для этой машины — 4–6. Это примерно число
   производительных ядер. Дальше ускорение растёт слабо, а эффективность сильно падает.
